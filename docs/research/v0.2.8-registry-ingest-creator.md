## Executive Summary

This deep dive grounds the four in-scope v0.2.8 groups (GH#25 registry ingest &
external identifiers, GH#26 creator/lab dimension, w3id.org IRI resolution, and
nomen multi-attestation) against their governing standards. **Every proposed
shape in #25 and #26 is confirmed spec-valid or spec-supported by prior art** —
there are no surprises that force a redesign, only a handful of precise
normalization rules to encode and one naming caveat (HuggingFace purl `version`
is a *git commit hash*, not a content digest; OCI purl `version` is the sha256
digest and is *required* to uniquely identify).

Headline findings: (1) the **package-url spec** now ships machine-readable JSON
type definitions — the `huggingface` and `oci` types are fully specified and the
#25 purl forms match them; (2) **SPDX's supplier/originator split** is near-exact
prior art for the #26 Provider(=supplier/distributor)/Creator(=originator)
distinction and validates the ruling that distributor collapses into Provider;
(3) **HuggingFace Hub** API rate limits are generous (500 API calls per anonymous
IP per 5-min window) so the existing ≥1s polite-bot cadence is comfortably
compliant, and the OpenAPI spec is the authoritative endpoint reference now;
(4) **w3id.org** is an apache-`.htaccess`-redirect + GitHub-PR service that fully
supports `Accept`-header content negotiation, so an entity IRI can resolve to
HTML for browsers and JSON-LD for machines from one perma-id; (5) **Wikidata's
per-claim multiple-references model** is the canonical prior art for lifting the
single-claim-per-triple limit — each reference attests the same value
independently, exactly the nomen multi-attestation shape #25 §4 wants.

Recommended direction: **Adopt** the purl type rules verbatim (they are now a
testable contract), **Adopt** SPDX-framed Creator-as-originator, **Adapt** the HF
Hub bot from the existing Ollama polite-bot template, **Adopt** w3id content
negotiation as the IRI resolution target (registration is a later, cheap step),
and **Adapt** the Wikidata reference-multiplicity model for nomen attestation.

## Topic Area 1 — GH#25: Registry Ingest & External Identifiers

### Subject A — package-url `huggingface` type (exact spec)

The purl spec migrated its type registry to machine-readable JSON definitions
(auto-generated `.md` mirrors live at
`package-url/purl-spec:docs/types/definitions/`). The `huggingface` type
(`Schema ID: https://packageurl.org/types/huggingfaces-definition.json`):

```
pkg:huggingface/<namespace>/<name>@<version>?<qualifiers>#<subpath>
```

| Field | Requirement | Case rule (verbatim) |
|---|---|---|
| namespace | **Required** | "the model repository username or organization, if present. **It is case sensitive.**" |
| name | **Required** | "the model repository name. **It is case sensitive.**" |
| version | Optional | "the model revision **Git commit hash**. It is case insensitive and **must be lowercased** in the package URL." |
| Default repo | — | `https://huggingface.co` (`repository_url` qualifier overrides) |

Canonical example: `pkg:huggingface/microsoft/deberta-v3-base@559062ad…`.

**Critical for bestiary:** the HF purl `version` is a *git commit revision*, **not
a content/manifest digest** (contrast OCI below). The #25 §1 proposal to mint
`pkg:huggingface/<org>/<repo>` *without* a version is spec-valid (version is
Optional) and is the honest choice when the bot records the repo identity but not
a pinned revision. If a revision is later captured it must be lowercased. The
`org`/`repo` segments are **case-sensitive** and must be preserved verbatim from
the Hub — do not lowercase them (a divergence from OCI). This directly feeds the
existing `NomenSchemeHuggingFace` machinery: the nomen `Value` is `org/repo`, and
`Format(SchemePURL)` derives the purl from it.

### Subject B — package-url `oci` type (exact spec, for Ollama)

The `oci` type (`Schema ID: https://packageurl.org/types/oci-definition.json`):

```
pkg:oci/<name>@<version>?<qualifiers>#<subpath>
```

| Field | Requirement | Rule (verbatim) |
|---|---|---|
| namespace | **Prohibited** | "OCI purls do not contain a namespace… `repository_url` may contain a namespace as part of the physical location." |
| name | **Required** | "not case sensitive and **must be lowercased**. The name is the **last fragment of the repository name.** … `library/debian` → name is `debian`." |
| version | Optional-but-effectively-required | "the **`sha256:hex_encoded_lowercase_digest`** of the artifact and **is required to uniquely identify** the artifact." |
| qualifier `repository_url` | Optional | "A repository URL where the artifact may be found… encouraged to identify a location the content may be fetched." |
| qualifier `tag` | Optional | "artifact tag that may have been associated with the digest at the time." |
| qualifier `arch` | Optional | package architecture when relevant. |

Spec examples show the `@` and `:` percent-encoded:
`pkg:oci/debian@sha256%3A244fd47e07d10?repository_url=docker.io%2Flibrary%2Fdebian&arch=amd64&tag=latest`
(one example leaves `sha256:` unescaped — encoders should percent-encode `:` in
the version).

**Validates #25 §2 exactly.** The proposed
`pkg:oci/<name>@sha256:<manifest-digest>?repository_url=registry.ollama.ai&tag=<tag>`
is correct, with two precise refinements the spec dictates:
1. **`name` must be lowercased and be the *last fragment*** — for Ollama's
   `library/llama3.1`, `name` = `llama3.1` (lowercased); the `library` prefix
   belongs in `repository_url` (`registry.ollama.ai/library`), not the name.
2. **version is the sha256 manifest digest and is what makes the purl unique** —
   the per-quant granularity #25 argues for is not just acceptable, it is
   *mandatory*: without the digest the purl does not identify the artifact. Each
   quant row's manifest digest → its own purl. This is why `pkg:oci` is honest
   for Ollama today and `pkg:huggingface` (revision-less) is honest for HF.

No registered `pkg:ollama` type exists (confirmed against the definitions
directory); the `oci` form is the correct vehicle. A future name-based
`pkg:ollama` proposal is cosmetic, as #25 notes.

### Subject C — HuggingFace Hub API (ingest mechanics)

The Hub API documentation has been **superseded by an OpenAPI spec** — the
authoritative, always-current reference is:
- `https://huggingface.co/.well-known/openapi.json` (machine)
- `https://huggingface.co/.well-known/openapi.md` (agent-readable markdown)
- Interactive: `https://huggingface.co/spaces/huggingface/openapi`

Established conventions (from Hub docs + `huggingface_hub` client behavior):
- **List endpoint:** `GET https://huggingface.co/api/models` with query params
  `author=<org>`, `filter=<tag>`, `search=`, `sort=`, `limit=`, `full=true`
  (full metadata incl. siblings/files), `config=true` (parse `config.json`).
- **Per-model:** `GET /api/models/<org>/<repo>` (and
  `/api/models/<org>/<repo>/revision/<rev>`). Model id **is** the `org/repo`
  path — a 1:1 mapping to the HF nomen `Value`, unlike the hard Ollama↔models.dev
  join. This is the *easy* identity direction (the alias-first join is still
  needed to attach an HF repo onto a bestiary *entity*, but the HF id itself
  needs no decomposition to form the nomen).
- **Pagination:** cursor-based via the **RFC 5988 `Link` header** (`rel="next"`);
  follow it rather than computing offsets.
- **ETag / caching:** Hub resolver responses carry `ETag` (backed by the LFS
  object SHA / git blob hash) and support conditional `If-None-Match` → `304`.
  The bot should send `If-None-Match` on re-runs to avoid re-downloading unchanged
  metadata (a politeness + determinism win).

### Subject D — Rate limits & polite-bot norms

Per the Hub rate-limits doc (as of the Sept-2025 revision):

| Request class | Anonymous (per shared IP) | Window |
|---|---|---|
| **API calls** (`/api/*`) | **500** | 5-minute fixed window |
| **Resolver** (file downloads) | 3,000 | 5-minute fixed window |

Over-limit → `429 Too Many Requests`. The existing `cmd/bestiary-ollama`
constraints — descriptive `User-Agent` and **≥1s between requests** — put the bot
at ≤300 requests / 5-min, **well under the 500 API-call ceiling**, so the current
polite-bot seam transfers unchanged. Recommend additionally: honor `429` with
backoff (respect `Retry-After`), send `If-None-Match`, and keep the metadata
sweep (`/api/models`) separate from any file/resolver hits. Optional HF token
raises limits but the anonymous path already suffices for a catalog-sized sweep.

### Subject E — Multi-source attestation of names (how other catalogs do it)

The `EntitySource` join-table + `DataSource` dimension bestiary already ships is
the standard relational shape. Cross-domain confirmation:
- **SPDX** records `supplier` (immediate distributor) *and* `originator` (point of
  origin) as separate `Person/Organization/NOASSERTION` fields per package — two
  provenance roles, not one (see Topic Area 2).
- **Wikidata** attaches N independent `reference` blocks to one statement, each a
  property-value set (`stated in` P248 / `reference URL` P854) — see Topic Area 4.
- **ecosyste.ms / SBOM tooling** key packages by purl and accumulate registry
  attestations per purl.

The lesson: keep the **join table as the source of truth** (one row per
entity×source), let purl/HF-form be *derived* nomina, and never collapse two
attesters into one row — precisely bestiary's existing `EntitySource` rule.

### Assessment

| Aspect | huggingface purl | oci purl (Ollama) |
|---|---|---|
| namespace | Required, **case-sensitive** (`org`) | **Prohibited** |
| name | Required, **case-sensitive** (`repo`) | Required, **lowercased**, last fragment |
| version | Optional, git commit (lowercased) | sha256 digest, **required for uniqueness** |
| repo location | default `huggingface.co` | `repository_url` qualifier (no default) |
| bestiary honesty today | repo id from HF bot (no revision) | manifest digest per quant row |
| #25 proposal status | ✅ spec-valid as-is | ✅ spec-valid (fix: lowercase name, digest required) |

**Adoption recommendation: Adopt** both purl type rules verbatim as a testable
contract (encode the case rules — HF preserves case, OCI lowercases the name —
and percent-encode `sha256:` in the OCI version). **Adapt** the HF Hub bot from
the Ollama polite-bot template; the id↔repo mapping is trivial (1:1) so the work
is the alias-first entity join + attestation minting, not the identity parse.

## Topic Area 2 — GH#26: Creator / Lab Dimension

### Subject A — SPDX supplier vs. originator (the near-exact model)

SPDX 2.x defines two distinct package-provenance roles, both
`Person|Organization|NOASSERTION`:
- **`PackageSupplier`** — "the actual distribution source… the immediate supplier
  of the package to the recipient." May differ from origin when repackaged.
- **`PackageOriginator`** — "if the package originated from a different person or
  organization than the Supplier, this identifies from where or whom the package
  **originally came**." Canonical example: *glibc → Supplier: Red Hat,
  Originator: Free Software Foundation.*

This is the **direct analogue** of the #26 ruling, translated to the model world:

| SPDX | bestiary | Role |
|---|---|---|
| `PackageSupplier` (distributor) | **Provider** (Groq/Anthropic/HF/Ollama) | who makes it available to you |
| `PackageOriginator` | **Creator** (Meta for Llama) | who trained/created the weights |

SPDX deliberately keeps these two fields and does **not** add a third "repackager"
role — repackaging is captured by supplier differing from originator. This
**validates the v0.2.7 Plan-UAT ruling** that *distributor collapses into
Provider* (no new dimension): distribution is a supplier-role property, and only
origination (Creator) earns a new typed field.

### Subject B — IFLA-LRM / schema.org / Dublin Core agent roles

- **IFLA-LRM** adds super-classes `Res` ("thing") and **`Agent`**, with roles like
  *creator* (`LRM-R2` created-by) and *publisher* attached at different WEMI-ish
  levels. Creation attaches to the intellectual content (the Work/Expression),
  publication to the Manifestation — mirroring bestiary's "creation is a fact
  about the **entity**, publication/serving a fact about the **instance/provider**."
- **schema.org:** `creator`/`author` (the agent that made the work) vs `provider`
  / `publisher` (the agent that supplies/distributes it) — the same split, widely
  used in JSON-LD.
- **Dublin Core / DCMI:** `dcterms:creator` vs `dcterms:publisher` — and #26/#25's
  downstream RDF-export motivation explicitly wants `dcterms:creator` as a
  predicate distinct from the serving deployment. Today only the serving side is
  truthfully populated.

All three converge on the same two-role ontology bestiary is adopting; the
Creator field maps cleanly to `dcterms:creator` / `schema:creator` /
`LRM Agent` for the RDF export, while Provider maps to
`schema:provider` / SPDX supplier.

### Subject C — HF model-card / ecosyste.ms lab attribution (the population signal)

- The **HF org segment** of `org/repo` is the strongest mechanical creator signal
  (`meta-llama/…` → Meta; `zhipuai/…` → Zhipu) — and #25's HF ingest surfaces it
  as a side effect, exactly as #26 notes. But org≠lab is common (mirror orgs,
  `TheBloke/` quant repos, community re-uploads), so it is a *signal*, not truth.
- **HF model-card metadata** (`base_model`, `license`, `model_creator` where
  present) and the existing `MetadataID` lab prefix (`zhipuai/glm-4.6`) are the
  curated-override feeders. The standing **curated > mechanical** precedent applies:
  derive from `MetadataID` prefix + HF org, override with a curated `creator`
  table for the mismatches.
- **Lineage** already carries the derivation half: a finetune's Creator differs
  from its base's Creator; the lineage edge supplies creator-of-derivation.

### Assessment

| Dimension | Provider (exists) | Creator (new, #26) |
|---|---|---|
| Question | who serves/distributes it | who trained the weights |
| SPDX analogue | supplier | originator |
| RDF predicate | `schema:provider` | `dcterms:creator` |
| Level | instance `(provider,host,region)` | **entity** |
| Population | ingest (models.dev/HF/Ollama) | MetadataID prefix + HF org + curated + lineage |
| Type today | `Provider` string | reuse `Provider` type via `Family.CanonicalProvider()` (the debt) |

**Adoption recommendation: Adopt** the SPDX supplier/originator framing as the
design vocabulary (cite it in the design record — it is the strongest prior art
and pre-answers "why doesn't distributor get its own dimension"). Introduce a
typed `Creator` (org) at the **entity** level, populated curated>mechanical from
the MetadataID lab prefix + HF org with a curated override table, and **retire
`Family.CanonicalProvider()`'s Provider-type reuse** by migrating consumers to
the entity-level Creator. Keep it additive (schema `$def` + entity prop, not
`required`, `BestiarySchemaVersion` bump). Whether `Creator` is a new distinct
type or a reused-but-renamed org type is an architecture decision — recommend a
**distinct `Creator`/`Org` type** so the compiler enforces the Provider/Creator
non-conflation the whole issue is about.

## Topic Area 3 — w3id.org IRI Resolution

### Subject A — Registration model & redirect mechanics

`perma-id/w3id.org` is a community-run permanent-identifier service (W3C
Permanent Identifier Community Group). Registration:
1. Fork the repo, create a directory named for your identifier path (e.g.
   `/bestiary/`), add an **`.htaccess`** (machine redirect rules) + **`README.md`**
   (human contact/description), open a **Pull Request**; maintainers merge.
   (Or email `public-perma-id@w3.org` with source URL, target, HTTP code.)
2. Once merged, `https://w3id.org/<path>` redirects per your `.htaccess`.

Requirements/norms: identifiers should be stable (never reused/repurposed),
the `.htaccess` uses Apache `mod_rewrite`, and you must supply a maintainer
contact. The redirect target is under your control (your own server / GitHub
Pages / a docs host).

### Subject B — Content negotiation (HTML vs JSON-LD)

w3id explicitly supports **`Accept`-header content negotiation** in `.htaccess`
without needing server-admin involvement — the canonical pattern:

```apache
# w3id .htaccess content-negotiation pattern
RewriteEngine On
RewriteCond %{HTTP_ACCEPT} application/ld\+json [OR]
RewriteCond %{HTTP_ACCEPT} application/json
RewriteRule ^entity/(.*)$ https://<host>/entity/$1.jsonld [R=302,L]
RewriteCond %{HTTP_ACCEPT} text/html
RewriteRule ^entity/(.*)$ https://<host>/entity/$1.html [R=302,L]
# default → machine representation
RewriteRule ^entity/(.*)$ https://<host>/entity/$1.jsonld [R=302,L]
```

Best practice for what an entity IRI should resolve to (linked-data "cool URIs"):
the IRI is a **non-information resource** (the model identity), which `303`- or
content-negotiation-redirects to a **description** — HTML for browsers, **JSON-LD**
for machines (Turtle/RDF optional). This lines up with bestiary's existing
`EntityRef.IRI(base)` (RFC 3987, percent-encoded canonical key under a
caller-supplied namespace): the base could become a `w3id.org/bestiary/` prefix,
and the resolution target is the entity's JSON-LD/HTML rendering.

### Assessment

| Aspect | Finding |
|---|---|
| Registration cost | Low — one GitHub PR (`.htaccess` + `README.md`) |
| Redirect engine | Apache `mod_rewrite`, `Accept`-header negotiation self-served |
| Resolution target | HTML (browser) + JSON-LD (machine), default machine |
| Fit with `EntityRef.IRI` | base namespace becomes `w3id.org/bestiary/`; IRI already total per entity |
| Blocker | Needs a stable public host serving per-entity HTML/JSON-LD |

**Adoption recommendation: Defer registration, Adopt the design target.** The IRI
minting already exists; w3id registration is a cheap, low-risk later step that
requires a public resolution endpoint (HTML + JSON-LD per entity) to exist first.
Design the IRI base and JSON-LD rendering now (it pairs with the RDF-export
motivation in #24/#25); file the w3id PR once a host serves the content. Do **not**
block v0.2.8 identity work on registration — the IRI is honest (asserts nothing
about retrievability) whether or not w3id is wired up yet.

## Topic Area 4 — Nomen Multi-Attestation

### Subject A — Wikidata per-claim references (the canonical model)

Wikidata's statement model: a statement = property-value(+rank), and **each
statement carries zero-or-more independent `reference` blocks**. Key property:
> "If there are many references for a claim, **each of them makes the claim
> independently from the others.**"

A reference is ≥1 property-value pair, typically `stated in` (P248) or
`reference URL` (P854). References can even back **contradicting** values (via
separate statements + ranks). This is precisely the shape #25 §4 wants: one
name-to-entity association (the "triple") attested by N sources, each attestation
standing on its own — not one authority overwriting another.

### Subject B — Library-science authority control

Traditional authority files (LoC/VIAF/MARC) record a preferred heading plus
variant/see-also forms, each with a **source citation** (MARC `670` "source data
found"). VIAF specifically *clusters* the same entity's headings **from multiple
national authority files**, keeping each contributor's attestation rather than
merging to one — the authority-control analogue of `EntitySource`. The preferred
heading = bestiary's `Preferred` canonical nomen; the variant forms with per-form
source citations = `Admitted` nomina with `SourceURL` + `Source`.

### Subject C — bestiary's current limit and the lift

CONCEPTS.md documents the v1 deviation: nomina keep **single-claim-per-triple**
(LRM models multiple attestations; "that is the named extension"). The v0.2.7
`nomina` store treats a same-triple conflict as a **loud codegen error** (curator
picks the authority). #25 §4: once two genuine attesters exist for one spelling
(curated + HF bot), lift to **attestation multiplicity**.

The Wikidata/VIAF model says how: the identity key of a nomen record is the
**triple `(Value, Scheme, ResolvesTo)`**; multiplicity lives in an *attestation
set* attached to it — each attestation carrying `(Source DataSourceID, SourceURL,
Status, ingested_at)`. Two sources asserting the same spelling → **two
attestations on one nomen**, not two nomina and not an error. A genuine
*disagreement* (same triple, conflicting `Status`) is resolved by rank/acceptability
(Wikidata rank; ISO acceptability), not by dropping one. The existing
`(SourceURL=who says, Source=where read)` two-level provenance already models a
single attestation's provenance — the lift is making that a **1-to-many** relation
under the triple.

### Assessment

| Model | Multiplicity mechanism | bestiary mapping |
|---|---|---|
| Wikidata | N independent `reference` blocks per statement | N attestations per nomen triple |
| VIAF authority | cluster headings from many national files | `EntitySource`-style per-source nomen attestation |
| bestiary v0.2.7 | single-claim-per-triple (conflict = error) | the limit being lifted |

**Adoption recommendation: Adapt the Wikidata reference-multiplicity model.**
Re-key nomen identity to the `(Value, Scheme, ResolvesTo)` triple with a child
*attestation set* (`Source`, `SourceURL`, `Status`, `ingested_at`) — the exact
parent/child shape v0.2.5's `entity_metadata`→`metadata_benchmarks/links` already
uses (replaceable child sets, delete-then-insert in the upsert txn). A same-triple
same-value multi-source case becomes two child rows (no error); a same-triple
*status* conflict is resolved by acceptability rank, not by curator-picks-one.
This is the documented LRM "named extension" and unblocks the curated+HF
dual-attestation #25 requires.

## Key Takeaways

### Adopt
- **purl type rules verbatim as a testable contract.** HF: `namespace`/`name`
  **case-sensitive** (preserve Hub casing), `version` = lowercased git commit
  (Optional → omit honestly). OCI: `name` **lowercased last fragment**, `version`
  = `sha256:<lowercase-digest>` **required for uniqueness**, `library` prefix →
  `repository_url`, percent-encode `sha256:` in the version. No `pkg:ollama` type
  exists — `pkg:oci` is correct.
- **SPDX supplier/originator framing for #26.** Cite it in the design record;
  Provider=supplier(+distributor), Creator=originator; maps to `dcterms:creator`
  for the RDF export. Introduce a **distinct** `Creator`/org type (not a reused
  `Provider`) so the compiler enforces non-conflation; retire
  `Family.CanonicalProvider()`'s Provider-type reuse.

### Adapt
- **HF Hub polite-bot** from `cmd/bestiary-ollama`: same `User-Agent`/≥1s seam,
  add `If-None-Match`/ETag conditional requests, follow the RFC-5988 `Link`
  pagination, back off on `429`. Authoritative endpoint ref is the OpenAPI spec
  (`/.well-known/openapi.json`), not the deprecated HTML docs.
- **Nomen multi-attestation** as parent-triple + child attestation set (Wikidata
  reference multiplicity), reusing the v0.2.5 `entity_metadata`→child-tables
  upsert pattern; resolve status conflicts by acceptability rank, not error.

### Defer
- **w3id.org registration** — design the IRI base (`w3id.org/bestiary/`) and the
  JSON-LD/HTML content-negotiated resolution now, file the PR once a public host
  serves per-entity descriptions. Pairs with the #24/#25 RDF-export thread.
- **Other registries** (ModelScope/Kaggle/NGC) — template repeats; no committed
  scope, evaluate per demand (#25 §3). Reserved-quant (`awq`/`gptq`/`int8`/`int4`)
  ingest rides in on the HF bot (#12 carry-over).
- **`pkg:ollama` purl-type upstream proposal** — cosmetic; `pkg:oci` works now.

### Skip
- **Nothing evaluated was rejected.** The one caveat to *not* do: do **not**
  lowercase HF `org`/`repo` (case-sensitive per spec) and do **not** mint an OCI
  purl without the manifest digest (version is what uniquely identifies) — both
  would produce spec-invalid identifiers.
